# 金仓数据库适配：AI 辅助研发经验总结

> 面向：研发中心内部　｜　分支：`feature/kingbase-V008R006C009B0014-pg-oracle`　｜　工具：Claude Code

## 一、背景与结果

| 项目 | 内容 |
|---|---|
| 任务 | ThingsBoard 适配人大金仓 KingbaseES V8（V008R006C009B0014） |
| 结果 | 支持 **pg、oracle** 两种兼容模式；**业务代码零改动，原 PostgreSQL 功能零影响** |
| 纯人工评估 | **32 人日**（普通开发，熟悉 PG、不熟悉金仓） |
| 本次实际 | **2 周（10 人日）**，一人 + Claude Code |
| 效果 | **节省约 22 人日，效率约 3 倍** |

本文重点不是"AI 写了多少代码"，而是**这件事换个人做会怎样、我为什么能快、哪些做法可以复用**。

## 二、如果换组里另一个人做

### 1. 工作量（纯人工评估）

| 阶段 | 人日 |
|---|---|
| 安装金仓环境 | 2 |
| 申请试用授权文件 | 1 |
| 初始化三种兼容模式（pg / oracle / mysql） | 2 |
| 熟悉金仓使用 | 1 |
| 摸底 + 适配开发 | 20 |
| 自测、修复等 | 6 |
| **合计** | **32** |

### 2. 最可能卡在哪

- **环境装好之后不知道从哪下手。** 金仓三种模式差异点分散在 SQL 函数、空串语义、大小写、运算符等各处，没有现成清单。
- **大概率直接让 AI "去适配"。** AI 会很积极地改代码、加方言、换驱动，改动面迅速扩大，最后很难说清楚对原有 PostgreSQL 功能有没有影响，回归成本反而更高。
- **在版本、模式、驱动上反复试错。** 这些坑我都踩过（见第四节），每个都要花时间验证后才能排除。

## 三、我的做法（5 步）

| 步骤 | 做了什么 | 关键点 |
|---|---|---|
| **1. 确认版本、搭环境** | 确认客户的数据库版本，让 AI 在机器上安装同版本金仓并初始化各兼容模式 | **版本必须精确到小版本**，否则模式都不一样 |
| **2. 摸底** | 让 AI 把 dao 层 950 个测试用例分别跑在 PostgreSQL 和金仓各模式上，逐项比对失败清单 | 用测试数据说话，不靠猜 |
| **3. 定位 + 决策** | AI 从报错中归纳根因；我决定支持范围、驱动和方言方案 | 人做取舍，AI 提供证据 |
| **4. 适配开发 + 验证** | AI 开发补丁和安装期自动处理逻辑，每次改完都在 **PostgreSQL / 金仓 pg / 金仓 oracle 多套环境矩阵**全量回归 | 每次都跑矩阵，保证 PG 零影响 |
| **5. 71 环境闭环实跑** | 在 10.8.8.71 实际部署运行，补 docker-compose 一键部署 | 实跑一次通过，没有出现新问题 |

最终代码量很小：**一个 3 行的 SQL 补丁 + 安装期自动探测逻辑 + 9 个单元测试**，运行期业务代码一行未改。

## 四、关键决策与踩过的坑

| # | 问题 | 怎么发现 / 怎么处理 | 经验 |
|---|---|---|---|
| 1 | **版本选错**：一开始装的大版本一致、小版本不同，只有 pg + oracle 两种模式 | 和客户版本核对后更换为 V008R006C009B0014，才出现三种模式 | 国产库小版本差异大，**第一步就要对齐到客户的精确版本** |
| 2 | **三种模式是否都支持** | mysql 模式实际试了约 **10 小时**，AI 做了大量实现；发现 `\|\|` 被当成逻辑 OR 且静默返回错误结果、大小写强制不敏感等问题，需要大改查询和方言 | **我决定本期不支持 mysql 模式**。AI 能把方案做出来，但做不做、代价值不值，要人来判断 |
| 3 | **驱动和方言怎么选** | 尝试过不同的驱动和方言组合，最终确认 **PG 官方驱动 + 原 PG 方言一套即可**同时支持 pg / oracle 两种模式 | 优先选改动最小的方案，不要一上来就换驱动、加方言 |
| 4 | **oracle 模式空串变 NULL** | **AI 在摸底中发现**：金仓 oracle 模式默认把空串当 NULL，导致写入报错、唯一性判断出错 | 通过连接串参数 `ora_input_emptystr_isnull=off` 解决，不用改代码 |
| 5 | **oracle 模式 448 个用例失败** | AI 从 2740 条报错中归纳出唯一根因：金仓 oracle 模式只自带两个参数的 `concat`，三个参数的调用全部报错 | 补一个 3 行 SQL 函数即可，安装时自动执行 |

## 五、为什么快：可复用的经验

1. **先定边界，再让 AI 动手。** 我给 AI 的第一条要求是"可以开发，但必须保证不影响原有功能"。这条原则决定了后面所有方案都往"最小改动"方向走，避免了大面积改代码。
2. **先摸底，后开发。** 先用全量测试在多套环境上跑出差异清单，再决定改什么。2740 条报错归结到一个根因，开发量从"大改"变成"3 行补丁"。
3. **每次改动都跑多环境矩阵。** AI 每次改完都在 PostgreSQL 和金仓各模式上全量回归。人工很难坚持每次都这样做，AI 可以，这是"零影响"有底气的原因。
4. **人做决策，AI 做执行。** 版本、支持范围、驱动方案这些取舍由我来定；装环境、跑测试、查日志、写代码、写文档交给 AI。mysql 模式就是 AI 做完实现、我判断代价后叫停的。
5. **AI 直接上机操作。** Claude Code 可以直接在服务器上安装、执行、看结果，省去了人工查手册、复制命令、来回传日志的时间。

## 六、下次适配其他数据库可以直接照做

1. 跟客户确认数据库的**精确版本**（含小版本）和要用的兼容模式。
2. 让 AI 在测试机安装同版本，初始化所有兼容模式。
3. 给 AI 定原则：**不影响原有功能，优先最小改动，不先换驱动、不先改方言。**
4. 让 AI 用现有全量测试在"原数据库 + 新数据库各模式"上跑出差异清单，并归纳根因。
5. 人根据差异清单和代价，决定支持范围和技术方案。
6. AI 开发，每次改动都在多环境矩阵全量回归。
7. 在真实环境部署实跑，补齐部署文档。
