## 2. 容量矩阵 —— 含 5 分钟全量快照（每设备 ≈151.2 点/秒）

**数字 = 最大可持续设备数**。`≥N` = 实测到 N 仍全绿、未找到墙；*斜体* = 由锚点档位插值（50ms/1000ms/2000ms 为实测锚点；500ms 介于 50~1000 之间取保守值，3000ms 与 2000ms 实测无差异）。

| flush 档位 | 71（160T/SSD） | 72（112T/SSD） | 68（32T/HDD） | 183（16T/HDD） |
|---|---|---|---|---|
| **50ms** | **≥12800**（194 万点/秒） | **≥10500**（159 万点/秒） | **≥6400**（97 万点/秒） | **≥2000**（30 万点/秒） |
| 500ms | *≥12800* | *≥10500* | *≈6800* | *≈2200* |
| **1000ms** | ≥6400 实测✅（未加压更高） | ≥5400 实测✅（未加压更高） | ≥4000 实测✅（未加压更高） | ≥1200 实测✅（未加压更高） |
| **2000ms** | **≥17500**（263 万点/秒，未到墙） | **12600~15000 之间**（12600✅=190 万，15000❌=226 万） | **7200~8400 之间**（7200✅=109 万，8400❌=123 万） | **2400~3000 之间**（2400✅=36 万，3000 时服务端已被 3600 预热压垮） |
| 3000ms | *≥17500* | *≈13000* | *≈7500* | *≈2400* |

> 1000ms 行的"未加压更高"：该档只做了抽检级（与同规模 2000ms 结果完全一致，吞吐差 <0.5%），实际上限应接近同机 2000ms 行。

## 3. 容量矩阵 —— 不含 5 分钟全量快照（每设备 =150 点/秒）

**实测结论：与含快照矩阵无可测差异（<1%），上表数字直接适用。**

四台机器各做了同规模对照（含快照 vs 纯 30% 变化，flush=2000ms）：

| 机器 | 含快照 | 不含快照 | 差异 |
|---|---|---|---|
| 71 @6400 台 | 95.9 万点/秒 ✅ | 95.9 万点/秒 ✅ | <1% |
| 72 @5400 台 | 81.4 万 ✅ | 80.9 万 ✅ | <1% |
| 68 @4000 台 | 60.3 万 ✅ | 59.9 万 ✅ | <1% |
| 183 @1200 台 | 18.1 万 ✅ | 18.0 万 ✅ | <1% |

原因：错峰快照只使平均速率 +0.8%（500÷300 ≈ 1.7 点/秒/设备），且 30% 随机变化本就让全部 500 条序列常驻活跃，快照不改变序列基数。**前提是快照必须错峰**——若全部设备同一秒发快照，瞬时速率为稳态 3.3 倍，等效于把设备数临时放大 3.3 倍去查上表。

## 4. 生产建议水位（重要——不要直接用上表极限值）

上表是 **300 秒浸泡**的短稳态结果。堆内存型劣化（memtable/合并债务随活跃序列数缓慢累积）需要 50 分钟以上才暴露——68 全栈环境曾实测"4000 台跑 50 分钟后 28G 堆耗尽雪崩"。按"每 100 万条活跃序列预算 ≥14G 堆"的长跑经验规则叠加限制：

| 机器 | 短稳态实测上限（300s） | **长跑保守水位（建议生产值）** | 约束来源 |
|---|---|---|---|
| 71 | ≥17500 台 | **≤9000 台**（136 万点/秒） | 64G 堆 ÷14G×100 万序列 ÷500 测点 |
| 72 | ~13000 台 | **≤6800 台**（103 万点/秒） | 48G 堆同上 |
| 68 | ~7800 台 | **≤4000 台**（60 万点/秒） | 28G 堆（与全栈实测雪崩点吻合） |
| 183 | ~2400 台 | **≤1400 台**（21 万点/秒） | 10G 堆（实测 3600 台预热即压垮服务端） |

要把长跑水位推向短稳态上限：加堆（71/72 内存充裕，堆可再翻倍）、上设备模板（schema/memtable 开销大降，另测 +25~50% 吞吐）、以及正式上线前按目标负载做 **≥1 小时**浸泡验证。

## 5. 口径说明与已知偏差（读数前必看）

1. **不含 TB 全栈开销**：本矩阵测的是"写缓冲 → IoTDB"存储链路。生产上 iotcloud（MQTT 接入+规则引擎）同机部署时要减掉它的 CPU/内存占用——68 全栈实测中 TB 侧在 60 万点/秒下额外消耗 ~6 核 + 8~16G 内存。TB 与 IoTDB 分机部署时上表更接近真实值。
2. **压测客户端与 IoTDB 同机**：客户端（写缓冲+tablet 构建）也消耗被测机 CPU，这部分与生产中 TB 进程的写缓冲开销等价，方向上是保守的。
3. **183 的 ❌ 是服务端崩溃不是渐进饱和**：10G 堆在 180 万序列预热突发下直接连接拒绝（疑似 OOM）。小内存机器的失效模式是猝死，水位务必保守。
4. **72 与 68 的 ❌ 是真实渐进饱和**：失败级别可见 flushAvg 秒级、积压百万级震荡——与 68 生产雪崩形态一致，判定可信。
5. 磁盘：HDD 机器（68/183）纯写入未见瓶颈（LZ4 顺序写压力小），但**查询负载并发时 HDD 会先于 CPU 成为瓶颈**，本矩阵未覆盖查询混合负载。
6. 数据真实性抽验：各机 `count timeseries` 与设备级 `select count` 落库点数均与提交量吻合，全程零写入失败（183 崩溃级除外）。

## 6. 复测方法

```bash
# 1) 被测机部署独立 bench IoTDB(端口 6668, 堆按 §1), 客户端 bundle 解压到 /root/bench
# 2) 预建 schema(新设备数必须先做, 否则创建风暴污染判定):
java -cp "bench-bundle/classes:bench-bundle/lib/*" org.thingsboard.server.dao.timeseries.iotdb.IotdbCapacityBenchmark \
  127.0.0.1:6668 <最大设备数> 500 150 300 20 <producers> 1000 2000 32 600000 0 max keep
# 3) 正式级(300s 浸泡; 不含快照把 300 改成 100000000):
java -cp "bench-bundle/classes:bench-bundle/lib/*" org.thingsboard.server.dao.timeseries.iotdb.IotdbCapacityBenchmark \
  127.0.0.1:6668 <设备数> 500 150 300 300 <producers> 1000 <flushMs> 32 400000 0 paced keep
```

producers 参考：16 线程机 4~6，32 线程机 8~10，百线程机 16~24。逐级抬升设备数直至 ❌，拐点 = 最后一个 ✅ 级别。

四台机器的原始日志留存于各机 `/root/bench/ladder*.log`（bench 容器已停止、数据卷保留，随时可复测）。
